## 1. 한눈에 보기

React Native/Expo 앱을 위한 **모바일 전용 백엔드**. `AGENTS.md`에 "웹은 제품 표면이 아니다"가 명시되어 있고, API 계약의 단일 진실은 `openapi/soundlog-api.yaml`이다.

```
클라이언트(Expo)
   │  https://soundlog.shop/api/soundlog  (Vercel 프록시)
   ▼
EC2 · docker compose
   ├── api (Express 5)  ──▶ ML 추천 서버 (http://211.188.54.204:8000/recommend)
   │                    ──▶ 한국관광공사 KorService2 (locationBasedList2)
   │                    ──▶ Nominatim (역지오코딩)
   └── db  (PostgreSQL 16)
```

**레이어**: `routes → middlewares(auth/validate/upload) → controllers(얇음) → services(두꺼움) → prisma`

핵심 특징은 **`apiService` 단일 분기점**이다.

```ts
// src/services/api.service.ts:5
export const apiService = env.USE_MOCK_DB ? mockSoundlogService : soundlogService;
```

컨트롤러 15개 전부가 `apiService`만 참조하므로 라우터·검증기·컨트롤러는 DB 모드를 모른다. 대신 **실 구현(4,036줄)과 mock 구현(2,782줄)이 51개 메서드를 각각 따로 구현**하는 구조 — 이게 뒤에서 다룰 여러 리스크의 뿌리다.

### 2.1 반드시 알아야 할 이름 매핑

`docs/recap-log-domain-contract.md`가 정의한 계약. **DB 이름과 제품 용어가 다르다.**

| 제품 의미 | 서버 이름 | 뜻 |
|---|---|---|
| **Recap** | Prisma `MomentLog`, `/v1/recap-captures` | 카메라 저장 **1회** |
| **Log** | Prisma `Recap`, `/v1/recaps` | 같은 `sessionId`를 가진 Recap의 집합 |
| Travel session | `TravelSession` | Log의 그룹 경계 + GPS 경로 수집 |

즉 `MomentLog`라는 이름을 보고 "Moment"라는 별도 개념을 만들면 안 된다. 핵심 불변식:

- `sessionId`가 없는 Recap = 독립 리캡 → **Log 목록(`GET /v1/recaps`)에 절대 안 나옴**
- Recap이 1개뿐인 세션도 유효한 Log
- Log 상세의 `moments`/`routePoints`에 다른 세션 데이터를 섞지 않음
- 비소유자에게는 `routePoints` 미반환, public 구성 Recap만으로 대표 장소·이미지·음악·개수를 **재계산**

이 12개 불변식은 `tests/api.test.ts`(약 490줄)와 `tests/seed-data.test.ts`가 실제로 강제하고 있다. 이 저장소에서 가장 잘 지켜지는 부분.

### 3.1 응답 규약

성공은 항상 `data`로 감싼다.

```
{ data: T }                                    // dataResponse
{ data: T[], page: { limit, nextCursor|null } } // 커서 페이징 (3곳뿐)
{ data: { accepted: true } }                   // 202 Accepted (6곳)
```

에러는 항상 `{ error: { code, message, details } }`. 코드는 **6종뿐** — `BAD_REQUEST(400)`, `UNAUTHORIZED(401)`, `FORBIDDEN(403)`, `NOT_FOUND(404)`, `DATABASE_ERROR(400)`, `INTERNAL_SERVER_ERROR(500)`.

409/422/**429가 없어서** 멱등성 경합, 동행 요청 24시간 쿨다운, 상태 전이 위반이 전부 400 하나로 뭉쳐 있다. 실질적 taxonomy는 `error.constants.ts`의 **한국어 메시지 41개**가 담당하며, 테스트도 `message.toContain('차단 관계')` 식으로 문자열을 매칭한다.

## 4. 음악 추천 파이프라인

`POST /v1/playlists/contextual` 기준 end-to-end:

```
멱등성 래핑(scope: playlist.contextual.create)
  └─ fetchMlRecommendationPlaylist(input)
       ├─ location 없음 → 즉시 undefined
       ├─ POST ML_RECOMMENDATION_API_URL  { mood, state, x:lng, y:lat }   (5초 timeout)
       ├─ 성공 → normalizeMlTracks → Playlist/Track upsert 영속화 → 사용자 like/save 상태 머지
       └─ 실패(5경로 전부 조용한 undefined)
             └─ findDefaultPlaylist  (규칙 기반)
                  ├─ placeId의 title/category/overview에 /해변|바다|해수욕장|ocean|beach/i → 'busan-ocean'
                  ├─ lat < 36.5 → 'busan-ocean'
                  └─ 그 외 → 'seoul-night'
```

응답 `context.source`로 `ml-recommendation` / `seed-fallback` 중 무엇이 쓰였는지 구분할 수 있다.

**여기서 발견된 것들:**

- ML 요청 본문이 **4개 필드뿐**(mood, state, x, y). 사용자 ID·청취 이력·선호 장르·제외 트랙을 보내지 않는다. 서비스 개요 문서에 적힌 "개인화 전환 전략"은 아직 서버에 반영되지 않은 상태.
- `excludeTrackIds`와 `preferredGenres`는 **검증기까지 통과하지만 코드 어디서도 사용되지 않는 죽은 입력**이다.
- `travelMode: 'festival'`은 검증기가 허용하지만 ML state 매핑 테이블에 없어 **무조건 `'산책'`으로 떨어진다**.
- 트랙 ID가 `sha1(artist:title:index)` — **인덱스가 해시에 포함**되어 같은 곡이 다른 순서로 오면 별개 Track 행이 생기고 좋아요/저장 상태가 분산된다.
- 응답 필드 오염: `placeName`에 `placeId`가 들어가고(`soundlog.service.ts:927`), `regionName`에 `'산책'` 같은 상태값이 들어가며(`:926`), `durationText`가 `"40:00분"` 형태로 생성된다(`:932`).
- `GET /v1/recommendations/playlists`가 `createContextualPlaylist`의 거의 완전한 복붙인데다, **GET인데 Playlist/Track 테이블에 쓰기를 한다**.

## 5. 한국관광공사 API 연동

- 엔드포인트는 **`KorService2/locationBasedList2` 하나뿐**. `arrange=E`(거리순), `radius` 기본 2000m, `numOfRows` 기본 10.
- `TOUR_API_SERVICE_KEY`가 없으면 조용히 로컬 `Place` 테이블로 폴백.
- TourAPI 결과가 있으면 하버사인으로 거리 재계산 → 반경 필터 → 정렬 → slice.

**주의할 점 3가지:**

1. **캐싱이 전혀 없다.** 매 요청마다 외부 API를 그대로 때린다.
2. **타임아웃이 없다.** ML 호출과 역지오코딩에는 `AbortController`가 있는데 TourAPI에만 없어서, 공공 API가 느려지면 Express 요청이 무한 대기한다.
3. **TourAPI 결과가 `Place` 테이블에 저장되지 않는다.** 그래서 `/v1/tour/nearby-places`가 준 `placeId`를 클라이언트가 `/v1/playlists/contextual`에 넘겨도 `prisma.place.findUnique`가 **항상 미스**하고, 장소 맥락 기반 폴백이 조용히 위도 규칙으로 떨어진다. 기획서의 "장소 맥락 → 음악" 연결에서 가장 아쉬운 구멍.

역지오코딩은 Nominatim이고, 1초 간격 직렬화 + 좌표 4자리(≈11m) 캐시(성공 24h/실패 5분)로 정책을 지킨다. 다만 캐시 `Map`에 eviction이 없어 장기 구동 시 메모리가 계속 증가한다.

## 6. Recap/Log 쓰기 흐름

### 멱등성

`IdempotencyRecord(scope, key, userId)` 유니크로 7개 스코프를 보호한다. 흐름은 `레코드 선-생성(response=null) → 액션 실행 → 응답 저장`, 실패 시 레코드 삭제.

두 가지 결함:
- 진행 중 폴링 윈도우가 **50ms × 10회 = 500ms**뿐인데 ML 타임아웃은 5,000ms다. 정상 처리 중인 요청을 클라이언트가 재시도하면 400 `IDEMPOTENCY_IN_PROGRESS`를 받는다.
- 비즈니스 쓰기와 멱등성 레코드 갱신이 **같은 트랜잭션이 아니다**. 그 사이에 프로세스가 죽으면 레코드가 `response=null`로 영구 고착되는데, **TTL/정리 로직이 없어서** 해당 키는 영원히 400만 낸다.

### 집계 재계산 (`refreshRecapAggregates`)

MomentLog 생성/수정/사진교체/삭제가 모두 트랜잭션 안에서 이 함수를 호출해 대표 장소·이미지·트랙·`momentCount`·가시성을 다시 계산한다. 계약 문서의 "삭제 후 일관성" 요구를 성실히 구현한 부분이다.

주의할 동작:
- **moments가 0개가 되면 Recap을 조용히 삭제**한다.
- public Recap에 공개+좌표 모먼트가 하나도 없으면 **자동으로 private로 강등**한다(역방향 자동 승격은 없음).
- `track.upsert({ update: {} })`이라 **이미 존재하는 Track의 title/artist는 절대 갱신되지 않는다** — 스냅샷이 바뀌어도 스테일.
- 공동 여행방 Recap은 moment JSON에 `location`/`visibility`가 없고 `travelSessionId`도 null이라 **public 전환 불가 + 재계산 대상에서 영구 제외**된다.

### 소유자 vs 비소유자

`getVisibleRecapMoments`가 게이트 역할을 하고, 비소유자에게는 `routePoints`·세션 시각을 제거하고 제목/대표값/개수를 공개 구성원 기준으로 다시 만든다. 다만 **공개 모먼트의 정확 좌표(`location`)는 그대로 반환**하므로, 경로는 가리면서 지점은 노출하는 비대칭이 있다.

## 7. 커뮤니티 & 안전 기능

Live Sound Map, 공동 여행방, 음악 취향 매칭, 동행 요청, 차단/신고까지 갖춘 상당히 큰 도메인이다.

- **핀 좌표 퍼징**: `Math.round(v * 100) / 100` (≈1.1km 격자). 정확 좌표는 별도 저장되고 본인에게만 노출.
- **매칭 스코어**: 기본 64점 → 무드/스타일 일치, 무드태그·트랙 보유, 거리(≤500m +8, ≤1500m +4), 최신성(≤30분 +6, ≤120분 +3)을 가산해 상한 96.
- **동행 요청 가드**: 자기 자신 금지 → 만료 핀 금지 → 차단 관계 403 → 기존 pending/accepted면 그대로 반환(멱등) → 최근 24시간 내 거절/취소 이력이면 쿨다운 400.
- **차단**: 양방향으로 해석하고 pending 요청을 일괄 취소.

**여기서 나온 이슈:**

- **퍼징 우회 가능.** 반경 필터와 매칭 스코어가 **정확 좌표**로 계산되므로, `lat/lng/radiusMeters`(100~20000)를 바꿔가며 `GET /v1/sound-map/nearby`를 반복 호출해 포함/제외를 관찰하면 정확 좌표를 이분 탐색으로 좁힐 수 있다. 응답의 `safety.exactLocationHidden: true`는 하드코딩 상수이고 실제 로직과 연결되어 있지 않다.
- **차단 필터가 3곳에만 적용된다** — 사운드맵 핀 조회, nearby 매칭, 동행 요청 생성. `GET /v1/recaps`, `/v1/recap-markers`, `/v1/recaps/:id/share`, 동행 요청 목록, 여행방 계열에는 적용되지 않아 **차단한 사용자의 공개 리캡이 지도·목록에 그대로 보인다**.
- **신고에 후속 조치가 없다.** 행만 생성하고 중복 방지·대상 존재 검증·자동 조치가 전무.
- `GET /v1/music-matches`가 내부에서 `getNearbySoundMatches`를 호출해 **API 1회당 이벤트 2건**이 기록된다. 게다가 이벤트 기록에 try/catch가 없어 **조회가 이벤트 기록 실패로 500**이 될 수 있다.

## 8. 인증

- 이메일/비밀번호 단일 방식, bcrypt cost **12**, `provider='email'` 고정.
- Access token: `{ sub: userId }`만 담은 JWT, 기본 1시간. 매 요청 DB 조회로 사용자 실존 확인.
- Refresh token: **384비트 난수 + SHA-256 해시 저장 + 1회용 회전 + User 삭제 시 cascade**. 이 부분 설계는 좋다.

**보완이 필요한 부분:**

- 재사용 탐지(reuse detection) 없음 — 이미 소비된 토큰이 재제출돼도 401만 낼 뿐 다른 세션을 무효화하지 않는다.
- 절대 수명 없음 — 매 refresh마다 30일이 새로 부여되는 무한 슬라이딩 세션.
- 만료 레코드 GC 없음 → `RefreshToken` 테이블 무한 증가.
- **비밀번호 변경/재설정 엔드포인트가 없다.** 유출 시 사용자가 자격증명을 회전할 방법이 계정 삭제뿐.
- `auth.middleware.ts`의 광범위 `catch`가 **DB 장애를 401로 위장**한다 → 장애가 전 사용자 강제 로그아웃으로 증폭되고, 5xx 지표에도 안 잡힌다.

### `ALLOW_DEV_AUTH_FALLBACK`

`true`이고 `NODE_ENV !== 'production'`이면 **Authorization 헤더가 아예 없는 요청이 공용 계정으로 자동 인증**된다. 즉 보호 엔드포인트 전체가 무인증 공개가 된다.

가드가 `NODE_ENV !== 'production'` 문자열 비교 단 하나인데 **`NODE_ENV`가 `z.string()`이라 enum 검증이 없다.** `Production`, `prod`, 오타, 미설정 어느 쪽이든 가드가 무력화된다.

## 9. 운영

### CI/CD

- **`pr-check.yml`**: install → `db:generate` → `typecheck` → `build` → `check:openapi-sync` → `check:no-spotify-metadata` → `test:coverage`. (build 이후에 spotify 검사를 두는 순서는 의도적 — 과거 `dist` 잔재가 구 동작을 서빙한 사고 대응)
- **`deploy-ec2.yml`**: Docker Hub 빌드/푸시 → SSH로 `production.env` 전달 → `compose pull && up -d` → **최대 3분 헬스체크** → Vercel 환경변수 동기화 → 컨테이너 내부에서 `check-public-api-contract` 실행 → SG 인그레스 자동 추가. 단일 인스턴스 in-place 교체이며 블루/그린·롤백은 없다.

### 가드 스크립트 5종 (팀의 실전 경험이 녹아 있는 부분)

| 스크립트 | 지키는 불변식 |
|---|---|
| `check-openapi-route-sync` | Express 라우트 집합 == OpenAPI 경로/메서드 집합 (현재 63개 통과) |
| `check-no-spotify-metadata` | `src/prisma/openapi/tests/**dist**`에 Spotify·재생제어 문자열이 없음 |
| `check-public-api-contract` | 배포된 서버가 실데이터를 주는지(mock/레거시 아님), 제거된 라우트가 실제 404인지 |
| `check-production-env` | `NODE_ENV=production`, `USE_MOCK_DB=false`, `ALLOW_DEV_AUTH_FALLBACK=false`, origin/업로드 URL HTTPS |
| `check-live-e2e` | 실 DB·파일 업로드·다중 사용자 권한·차단 로직까지 도는 621줄 시나리오 |

### mockDB 모드

`USE_MOCK_DB=true`면 PostgreSQL 없이 인메모리 데이터로 같은 응답을 낸다. 단순 스텁이 아니라 가시성·차단·쿨다운·집계 재계산까지 재구현한 병렬 구현체다. 타입 시그니처는 `apiService` 삼항 연산 덕에 `typecheck`가 강제한다.

**단, 동작 동등성을 검증하는 테스트는 0건이다.** 실제로 벌어진 발산:

- 멱등성이 4개 스코프에서 누락(`playlist.contextual`, `library.track`, `recommendation-events`, `recap-share-event`)되고, "진행 중" 상태 자체가 없어 `IDEMPOTENCY_IN_PROGRESS`가 mock에서는 발생 불가.
- `mock-soundlog.service.ts:906-907`의 `deleteMyAccount`가 `libraryTrackStates`와 `momentLogs`를 **userId 무관 전체 삭제**한다 (바로 아래 줄부터는 전부 userId로 필터링). A가 탈퇴하면 B의 데이터가 사라진다.
- mock refresh token이 사용자에 바인딩되지 않아 **임의의 유효 refresh token이 "가장 최근 로그인 사용자"의 access token을 발급**한다.
- ML 연동이 없어 `source: 'ml-recommendation'`이 mock에서는 절대 생성되지 않는다.

## 10. 발견 사항 (우선순위)

### Critical

| # | 내용 |
|---|---|
| C-1 | `docker-compose.yml:28,33` — `.env` 없이 뜨면 **`NODE_ENV=production` + 공개 저장소에 적힌 JWT 시크릿(`change-me-in-local-development`)**으로 기동한다. 이 값을 아는 사람은 `{"sub": "<임의 userId>"}`로 토큰을 위조해 모든 계정을 탈취할 수 있다. `POSTGRES_PASSWORD` 기본값도 동일 문제. (`docker-compose.prod.yml`은 기본값 없이 `${JWT_SECRET}`이라 정상) |
| C-2 | `POST /v1/dev/db-test-records`에 **`authMiddleware`가 없다**. `payload`가 임의 JSON이라 인터넷 누구나 요청당 1MB를 무제한 행으로 DB에 적재 가능. OpenAPI에도 `security: []`로 선언되어 있어 sync 가드가 잡지 못한다 |
| C-3 | **rate limiting 전무.** 로그인 무제한 브루트포스가 가능하고, bcrypt cost 12(요청당 수백 ms CPU)와 결합되면 로그인 폭주만으로 단일 EC2를 CPU 고갈시킬 수 있다. `app.set('trust proxy')`도 없어 지금 리미터를 넣어도 프록시 뒤에서 IP 식별이 안 된다 |

### High

| # | 내용 |
|---|---|
| H-1 | **프로덕션 API 전체가 평문 HTTP.** compose에 TLS 종단이 없고 SG를 `0.0.0.0/0`으로 여는데, 로그인 비밀번호·Bearer 토큰·사진 URL이 모두 암호화 없이 오간다. `check-production-env`의 HTTPS 강제와 정면 충돌 — 실제 배포 설정은 이 가드를 통과할 수 없다 |
| H-2 | **`check:production-env`가 어떤 CI/CD 단계에서도 실행되지 않는다.** README에만 존재. 게다가 `docs/ec2-deployment.md`가 권장하는 `PRODUCTION_ENV` 예시에 `http://localhost:8081`이 프로덕션 CORS allowlist로 들어가 있어 문서와 가드가 서로 어긋난다 |
| H-3 | **실 서비스 코드 4,036줄이 CI에서 한 줄도 실행되지 않는다.** `pr-check.yml`이 `USE_MOCK_DB=true`로만 돌고 Postgres 서비스 컨테이너도 없으며, `vitest.config.ts:8-10`이 `soundlog.service.ts`를 커버리지에서 **명시적으로 제외**한다. 70% 임계치는 mock 구현만으로 충족된다 |
| H-4 | multer가 zod 검증보다 **먼저** 실행되어, 400이 나도 파일은 이미 디스크에 남는다. 정리 로직·GC 배치가 없어 유효 토큰 하나로 볼륨을 채울 수 있다 |
| H-5 | 사용자 열거 — `register` 중복 시 `USER_ALREADY_EXISTS` 명시 반환, `login`은 계정 존재 여부에 따라 bcrypt 수행 유무가 갈려 **응답 시간 차이로 가입 여부 판별** 가능. C-3(제한 없음)과 결합되면 이메일 목록을 뽑아낼 수 있다 |

### Medium

- 업로드에 `fileFilter`(MIME 검증)와 `files/fields/parts` 제한이 없다. multipart는 `REQUEST_BODY_LIMIT` 적용 대상도 아니다. (확장자 없는 랜덤 파일명 + helmet `nosniff` 덕에 저장형 XSS는 대체로 막히지만, 의도된 방어가 아니라 부수 효과다)
- `express.static(uploads)`에 접근 제어가 없어 리캡이 `private`여도 **사진 파일 자체는 URL만 알면 누구나** 받을 수 있다.
- `deploy-ec2.yml:65-67` — `workflow_dispatch` 입력이 셸에 직접 보간되고, 정규식 검증은 **그 이후**에 실행된다. 같은 워크플로 다른 곳에서는 올바른 `env:` 패턴을 쓰고 있어 일관성도 깨져 있다.
- `deploy-ec2.yml:6-7` — 개인 브랜치 `codex/server-deploy-contract-check-fix` push가 **리뷰 없이 프로덕션에 자동 배포**된다. 디버깅 잔재로 보인다.
- `production.env` → `.env` 이동 시 `chmod 600`이 없고, `docker logout`도 없어 EC2에 Docker Hub 토큰이 잔류한다.
- Prisma 오류 전체를 **400**으로 매핑해 서버 장애가 5xx 지표에 안 잡힌다. `res.headersSent` 체크도 없다.
- `paginateByCursor`가 커서를 못 찾으면 `findIndex → -1 → +1 = 0`이 되어 **조용히 1페이지로 되돌아간다**. 항목이 삭제되면 클라이언트가 무한 루프에 빠질 수 있는데, 테스트에 `cursor`가 **한 번도 등장하지 않는다**.
- **인메모리 페이지네이션**: `getRecapMarkers`가 전체 public recap을 `take` 없이 로드한 뒤 메모리에서 거리 필터를 건다. `getRecaps`, `getMomentLogs`, `getLibraryTracks` 등도 동일.
- 필터보다 `take`를 먼저 적용: 사운드맵은 `take: 50` 후 반경 필터라 최근 갱신 50개 밖의 근처 핀은 절대 안 보인다.
- Swagger UI와 `/openapi.yaml`이 프로덕션에서 무인증 공개.

### 관측성

`soundlog.service.ts` 전체에 로깅 호출이 **0건**이다. 외부 연동 3곳(ML·TourAPI·Nominatim)이 모두 예외를 빈 값으로 삼켜서, **ML 서버가 죽어도 사용자는 시드 폴백을 받고 운영진은 알 방법이 없다.** ML이 `undefined`를 반환하는 경로가 5개인데 전부 구분 불가하다. 프로덕션 morgan 포맷도 `dev`(타임스탬프·IP·UA 없음)다.
